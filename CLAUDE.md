# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Docker is the preferred way to *run* the app (see `Dockerfile` / `docker-compose.yml`); `uv` is for local development (tests, lint, editing with reload). The app requires a one-time Authentik bootstrap first — see README.md's "Authentication setup" section — and fails to start without `SESSION_SECRET_KEY`/`AUTHENTIK_*`/`POSTGRES_PASSWORD` env vars set. `docker compose up` brings up `pronunciation-coach-db`, runs the one-shot `pronunciation-coach-migrate` to completion, and only then starts the app. Running natively needs a reachable Postgres — easiest is `docker compose -f docker-compose.dev.yml up -d pronunciation-coach-db`, which publishes on host port 55432.

```bash
HOST_UID=$(id -u) HOST_GID=$(id -g) docker compose up -d --build   # build + run (preferred)
docker compose logs -f                                             # tail logs
docker compose down                                                 # stop and remove

uv sync                    # install/update dependencies
uv run alembic upgrade head          # apply migrations — the app no longer creates its own schema
uv run alembic revision --autogenerate -m "..."   # after editing app/models.py; read the result before committing
uv run alembic check                 # models-vs-migrations drift (also runs as a test)
uv run fastapi dev         # dev server with reload (entrypoint from [tool.fastapi] in pyproject.toml)
uv run fastapi run         # production server, native
uv run playwright install chromium   # one-time, for the browser-driven frontend tests
uv run pytest              # run all tests
uv run pytest -m "not frontend"      # skip the browser layer
uv run pytest app/tests/test_frontend.py   # browser layer only (no model load)
uv run pytest app/tests/test_scoring.py::test_identical_text_scores_100   # single test
uv run ruff check .        # lint
uv run ruff format .       # format
```

No separate build step — the frontend is plain static files served directly by FastAPI.

## Architecture

This is a local FastAPI app: record yourself saying an English phrase, get a phoneme-level pronunciation score. It requires login (OIDC via Authentik) and scopes attempt history/stats per authenticated user.

**Scoring pipeline** (the core of the app, spans `app/ml.py`, `app/scoring.py`, `app/routers/attempts.py`): uploaded audio → `faster-whisper` transcribes it to text → `app/scoring.py` normalizes both the target phrase and the transcript into word lists → `g2p_en` converts each word *individually* to ARPAbet phonemes (called per-word, not per-sentence, to avoid the `" "` separator tokens `g2p_en` inserts between words on sentence input) → `difflib.SequenceMatcher` aligns reference/hypothesis word lists (equal/replace/delete/insert opcodes map to correct/mispronounced/missing/extra) → phoneme-level edit distance per aligned word pair produces a 0–1 word score → the overall 0–100 score is the mean word score across all non-`extra` words.

**Model lifecycle**: `WhisperModel` and `G2p` are both expensive to load and are instantiated exactly once, in `app/main.py`'s lifespan, and stashed on `app.state`. Request handlers reach them via the `WhisperModelDep`/`G2pDep` dependency aliases in `app/ml.py` — never re-instantiated per request. The Whisper model defaults to `small.en` / `compute_type="int8"` / `device="cpu"`, overridable via the `WHISPER_MODEL_SIZE` / `WHISPER_COMPUTE_TYPE` env vars.

**Self-contained runtime data**: `app/config.py` computes every runtime path (saved recordings, Whisper model cache, nltk data) under `data/`, and sets the `NLTK_DATA` env var *before nltk is ever imported anywhere in the process* — order matters here, since nltk's `default_download_dir()` only picks a directory that already exists on disk at first use, and always falls back to `~/nltk_data` otherwise. The whole `data/` root is overridable via `PRONUNCIATION_COACH_DATA_DIR` (this is how tests get an isolated runtime).

**nltk is pinned `<3.9`**: `g2p_en`'s own downloader requests the legacy `averaged_perceptron_tagger` resource, but nltk ≥3.9 looks up `averaged_perceptron_tagger_eng` by default — a mismatch that surfaces as a `LookupError` on first real use, not at import time. `ensure_nltk_data()` in `app/ml.py` defensively tries both resource names as a second line of defense.

**Frontend**: plain HTML/CSS/JS in `frontend/`, no bundler. Served via `router.frontend("/", directory=...)` on a dedicated `APIRouter(dependencies=[Depends(require_web_session)])` in `app/main.py`, mounted *after* the API routers so it never shadows `/api/*` — a low-priority static route that only matches once no other route does.

**Authentication** (`app/auth.py`, `app/routers/auth.py`): backend-driven OIDC Authorization Code flow against Authentik via `authlib`'s Starlette `OAuth` client — `/auth/login` redirects to Authentik, `/auth/callback` exchanges the code, upserts a local `User` row keyed by the OIDC `sub` claim, and stores `user_id` in a signed session cookie (Starlette's `SessionMiddleware`; tokens never reach the browser JS). **Logout is RP-initiated, not local-only**: `/auth/logout` clears the local session and then redirects to Authentik's `end_session_endpoint` (discovered from the OIDC metadata, never hardcoded) with `post_logout_redirect_uri` and an `id_token_hint` — the `id_token` is stashed in the session at callback purely for that hint. Clearing only our own cookie is *not* enough: Authentik keeps its own session, so the subsequent redirect to `/auth/login` gets silently re-authorized and drops the user straight back into a logged-in app, making Logout look like a no-op. This also depends on the Authentik provider using `default-invalidation-flow`, **not** `default-provider-invalidation-flow` — the latter ships with no stages bound to it and ends only the per-application session (see `authentik-blueprints/pronunciation-coach.yaml`). If the metadata fetch fails, logout degrades to a plain redirect to `/` rather than 500ing. Two dependencies share one resolver: `get_current_user` (401 JSON, used by `/api/*` and testable via `app.dependency_overrides`) and `require_web_session` (raises `WebAuthRequired`, caught by an `app.add_exception_handler` that 302s to `/auth/login?next=...`, used by the frontend router). **Key fact this relies on**: FastAPI's `router.frontend()` genuinely runs router-level `dependencies=[...]` through the normal dependency-injection machinery before serving a matched static file (`_FrontendRouteGroup.handle()` in `fastapi/routing.py`) — confirmed by reading the installed FastAPI source, not assumed — which is why gating the whole app needs no hand-rolled ASGI middleware. `/docs`/`/redoc`/`/openapi.json` are unaffected (they're default routes on `app`, never part of the frontend router), so the Dockerfile healthcheck (`GET /docs`) needs no auth.

**Data model** (`app/models.py`): `Phrase` (unique `text`, `difficulty`, `category`), `User` (`sub` unique/indexed, `email`), `Attempt` (FK to `phrase` and `user`, `transcript`, `score`, `word_feedback` stored as a `JSONB` column), and `UserPreference` (one row per user — `user_id` FK is `unique`, so the upsert in `app/routers/preferences.py` can query by user and never has to disambiguate duplicates). Four Postgres-specific choices are deliberate and each has a comment at the definition site: (1) `User.__tablename__ = "app_user"` because `user` is a reserved word — `SELECT * FROM user` is a *syntax error*, not a table scan; (2) `Difficulty` is `sa.Enum(..., native_enum=False)`, i.e. VARCHAR, so adding a difficulty is an ordinary column edit rather than `ALTER TYPE ... ADD VALUE` up plus a hand-written `DROP TYPE` down (autogenerate emits neither); (3) `word_feedback` is `postgresql.JSONB`, not the generic `sa.JSON` — that compiles to PG `json`, which re-parses on every read and **has no `=` operator**, so any future `WHERE`/`DISTINCT` over it errors. Do *not* "keep it portable" with `with_variant()`: Alembic loses the variant and `alembic check` then reports a perpetual diff; (4) all four datetime columns are `TIMESTAMPTZ`, because every value written is an aware `datetime.now(UTC)` and psycopg3 adapts those with the `timestamptz` OID — assigning that to a naive column is an implicit cast Postgres runs *through the session's TimeZone GUC*, so what actually landed on disk would depend on a setting nobody thinks about. The visible effect is API timestamps carrying `+00:00`; nothing in `frontend/app.js` reads `created_at`.

**Database & migrations** (`app/config.py`, `app/db.py`, `alembic.ini`, `app/alembic/`): PostgreSQL via `psycopg3` (`postgresql+psycopg://`). `config._database_url()` returns `DATABASE_URL` verbatim when set, otherwise assembles one from `POSTGRES_HOST`/`PORT`/`DB`/`USER` (all defaulted) plus a required-no-default `POSTGRES_PASSWORD`, using `URL.create()` rather than an f-string so a password containing `:@/?` is percent-encoded instead of corrupting the URL. The engine sets `pool_pre_ping=True` (a Postgres server drops pooled connections out from under you; a SQLite file never did) and `-c timezone=utc`.

**The schema is Alembic's, and `SQLModel.metadata.create_all()` is gone** — `app/main.py`'s lifespan now only seeds. Migrations run explicitly (`uv run alembic upgrade head`, or the one-shot `pronunciation-coach-migrate` compose service), so a bad migration fails on its own instead of crash-looping the app on boot. Seeding stays *in* the lifespan on purpose: it's data the app owns, it's idempotent, and it reconciles drifted rows — freezing 133 phrases into a migration would mean a new revision per phrase edit. Three things about the Alembic setup are load-bearing: `app/alembic/env.py` **imports `app.models`** (without it autogenerate diffs against empty metadata and writes a migration that drops every table); it builds its own engine with `create_engine()` rather than `engine_from_config()`, because `alembic.ini` is parsed by ConfigParser, which treats `%` in a password as interpolation syntax; and `alembic.ini` deliberately has **no `sqlalchemy.url`** — `env.py` takes it from `app/config.py`, so one place builds the URL and no password lands in a committed file. `app/__init__.py` installs a constraint `naming_convention` on `SQLModel.metadata`, and it must be there rather than in `models.py`: SQLAlchemy resolves a constraint's name when it's *attached* to its Table, i.e. while the model class body runs, and the package `__init__` is the only module guaranteed to execute first. That's what gives `pk_phrase`/`fk_attempt_user_id_app_user` instead of dialect-generated names. `alembic.ini`'s `post_write_hooks` run `ruff check --fix` + `ruff format` on each generated revision, so autogenerate's unsorted import block and its unconditional `import sqlmodel` don't need a per-file lint ignore (hooks fire on `revision` only, never `upgrade`, so the `--no-dev` image never needs ruff).

**User preferences** (`app/routers/preferences.py`, `frontend/app.js`): `GET`/`PUT /api/me/preferences` read and store the difficulty/category filter selection. `PUT` is a **full replacement** — an omitted field is stored as "no filter", not left alone — which matches how the frontend always sends both selects, and `""` (what an HTML `<select>`'s "Any" option submits) is normalized to `NULL` on write so it can't become a category no phrase matches. `GET` for a user who has never chosen anything returns the same `{difficulty: null, category: null}` shape as one who explicitly chose "Any", so the frontend needs no special case. The category filter is fed by `GET /api/phrases/categories` (distinct non-null categories, sorted). Two ordering constraints in `app.js`'s `init()`, both load-bearing: categories must be fetched *before* preferences (a saved category can only be selected once its `<option>` exists — `hasOption()` guards the case where a saved value is no longer offered at all, which would otherwise silently select nothing), and preferences before the first `loadRandomPhrase()` (otherwise the opening phrase ignores the restored filters and visibly swaps out). Every one of these fetches degrades silently to the unfiltered default rather than blocking startup. `app/seed_data.py` seeds 133 built-in phrases (20 categories × 3 difficulties, grouped in the file by category) idempotently on every startup, keyed off the unique `text` column. **Because the idempotency key is `text`, inserting isn't enough**: editing a seeded phrase's `category`/`difficulty` would never reach an existing DB, so `seed_phrases()` also reconciles drifted rows back to the seed list — that's what made the `technology` → `information-technology` rename actually apply instead of leaving both slugs in the dropdown. Category slugs are lowercase-hyphenated and reach the UI as `option.value`; `categoryLabel()` in `app.js` derives the display text (sentence case), so there's no slug → label map to maintain. (A `rename_technology_preferences()` stopgap used to carry a saved `"technology"` `UserPreference` across that rename; it was deleted with the Postgres move, since revision 1 *creates* the tables and no Postgres database can ever hold the stale value.)

**Audio playback / TTS** (`frontend/app.js`, `frontend/index.html`): browser-native `SpeechSynthesis`, no backend involvement — `#speak-btn` plays the whole target phrase, and words in the **per-word feedback results** (not the phrase display, which stays a plain `textContent` assignment) play on hover-after-700ms or on click. Several non-obvious things hold this together. `stopSpeaking()` clears *both* the pending hover timer and the in-flight utterance, and is called from **inside `speak()`**, so no caller has to remember it — `speechSynthesis.cancel()` alone would leave an armed `setTimeout` to fire later, which is the subtle half. The cancel on phrase change lives at the `textContent` wipe in `loadRandomPhrase()`, **not** in `renderPhrase()`: `renderPhrase` only runs after an unbounded `await fetch`, so a hover armed just before "New phrase" would fire during the fetch window, and the failure path never reaches `renderPhrase` at all. Speakable words are marked with a **`data-speak` attribute rather than a class**, because `test_frontend.py` asserts `to_have_class("word {status}")`, which matches the entire class attribute — an extra class breaks four assertions. Listeners are delegated onto `#feedback-words` (`renderFeedback()` rebuilds the spans every attempt) using `mouseover`/`mouseout`, since `mouseenter`/`mouseleave` don't bubble. `speak()` refuses while `state.isRecording` and `#speak-btn` is disabled then too: speaker output feeds straight back into `getUserMedia`, so playing audio mid-recording corrupts the very attempt about to be scored. The 700ms delay is also deliberately above Chrome's ~500ms native `title` delay, so a word's phoneme tooltip lands before its audio rather than racing it; don't drop it below ~550ms. Every entry point guards on `window.speechSynthesis && window.SpeechSynthesisUtterance` and degrades to a silent no-op — headless Chromium has the API but zero voices, and `test_no_uncaught_page_errors_on_load` fails on anything thrown. Note `.icon-btn` sets `display: flex`, which **beats the UA stylesheet's `[hidden] { display: none }`** — hiding an icon button would need an explicit rule (`#user-menu` dodges this because the hidden element is the wrapper, not the button).

**Docker**: `docker-compose.yml` bind-mounts `./data:/app/data`, so saved recordings and the downloaded Whisper/nltk caches are shared between Docker and native runs and survive container rebuilds. The container runs as `${HOST_UID}:${HOST_GID}` (defaulting to 1000:1000) rather than root, specifically so files written into that bind mount are owned by the host user instead of `root` — set `HOST_UID`/`HOST_GID` (e.g. via a gitignored `.env`) to your actual `id -u`/`id -g` if they differ from 1000. The **database is not in that bind mount**: `pronunciation-coach-db` keeps it in a named volume, because Postgres manages its own on-disk format and its image runs `initdb` as root before dropping privileges (so it must *not* get the `user:` override the app service has). Consequence worth knowing: `docker compose down -v` now destroys practice history, which the old bind-mounted SQLite file survived. A one-shot `pronunciation-coach-migrate` service runs `alembic upgrade head` and exits; the app `depends_on` it with `service_completed_successfully` and on the db with `service_healthy`. Both share the same `image: pronunciation-coach:local` tag and an `x-app-env` YAML anchor, so the migration is guaranteed to be the exact code the app then runs, and Alembic's `env.py` (which imports `app/config.py`) gets the auth vars it transitively needs. The db healthcheck uses a tighter 5s interval than `authentik-db`'s 30s because `up` blocks on it twice over. `docker-compose.dev.yml` mirrors all of this with hardcoded dev-only secrets, `-dev` volume names, and publishes Postgres on host port **55432** so a native `uv run fastapi dev` / `uv run alembic` can borrow it.

**Test isolation** (`app/tests/conftest.py`): sets `PRONUNCIATION_COACH_DATA_DIR` to a fresh temp dir, `DATABASE_URL`, plus dummy `SESSION_SECRET_KEY`/`AUTHENTIK_*` values (required, no-default config — see Authentication above), as top-level module code — this must run before `app.config` (and therefore `app.main`) is imported anywhere, including by other test files, which is why it happens before any other import in the file. **The key insight that makes the Postgres setup work**: `create_engine()` does not connect, so only the *URL* has to exist at import time (`app/db.py` builds the engine there), not a running server — which is what lets the container start lazily in the session-scoped `database` fixture instead of on every `pytest` invocation. `database` starts a throwaway `postgres:16-alpine` via `testcontainers` bound to a fixed host port (55432, so the URL is knowable in advance), calls `_reset_schema()` then `_upgrade_to_head()`, and stops it in a `finally`. `PRONUNCIATION_COACH_TEST_DATABASE_URL` points at an already-running Postgres and skips the container entirely; note conftest **assigns** `DATABASE_URL` rather than `setdefault`-ing it, since a developer's exported `DATABASE_URL` points at their real database and `_reset_schema()` would drop it (it also refuses any database whose name lacks `test`). `_reset_schema()` calls `engine.dispose()` afterwards because psycopg3 auto-prepares statements and a pooled connection outliving its schema fails with "cached plan must not change result type". Only tests reaching the DB request `client` (which now depends on `database`), so the `frontend`-marked tests never start Docker; `test_scoring.py`'s two real-G2p tests use a separate `g2p` fixture for the same reason. There is deliberately **no per-test rollback** — one shared database per run with rows accumulating, exactly as the old SQLite temp file behaved, so no existing assertion changes meaning. The tradeoff to know: on Postgres a duplicate-key insert aborts the *surrounding transaction*, so one bad insert cascades into `current transaction is aborted` errors in unrelated tests. The session-scoped `client` fixture then runs the app's real lifespan via `with TestClient(app)`, creates one real `User` row, and overrides `get_current_user` via `app.dependency_overrides` to return it — `authlib` only fetches OIDC `.well-known` metadata lazily on first `authorize_redirect`/`authorize_access_token` call (confirmed by reading the installed `authlib` source), so this never touches a real Authentik instance. Tests needing a *different* user (e.g. proving per-user scoping in `test_auth.py`) temporarily swap the override and restore it in a `finally` block.

**Frontend tests** (`app/tests/test_frontend.py`, marked `frontend`): headless Chromium via `pytest-playwright`, driving the real shipped `frontend/` files. They deliberately **do not start the FastAPI app** — a bare `ThreadingHTTPServer` (the `frontend_server` fixture) serves `frontend/`, and the `api` fixture intercepts every `/api/*` call in the browser with canned responses. That keeps the whole Whisper/G2p model load out of this file, so it runs in ~15s versus ~40s for anything touching the `client` fixture. Two things worth knowing before editing it: (1) the interception is **one** `page.route("**/api/**", ...)` dispatching on path/method, not one route per endpoint, because Playwright matches routes in *reverse* registration order and `**/api/attempts/stats` vs `**/api/attempts/?limit=20` would otherwise shadow each other; (2) `conftest.py` overrides `browser_type_launch_args` to add `--use-fake-device-for-media-stream`/`--use-fake-ui-for-media-stream`, which is what lets the tests exercise the genuine `getUserMedia` + `MediaRecorder` path instead of stubbing it — only the mic-permission-denied test injects a stub, via `page.add_init_script`; (3) the TTS tests **must** stub `window.speechSynthesis` (the `stub_speech` helper, same `add_init_script` mechanism) because headless Chromium ships the API with no voices, so a real `speak()` is an unobservable no-op — unlike `getUserMedia`, where the fake-device flags make the genuine path work. `SpeechSynthesisUtterance` is deliberately left *un*stubbed so the real constructor and the `lang` assignment are exercised. Note that `loadHistory`/`loadStats` in `app.js` have no `res.ok` check, so their "Could not load…" fallbacks are only reachable via a *failed* request or an unparseable body, never a 500 with valid JSON — hence the `network_error()`/`malformed_json()` helpers. Server-side frontend wiring (auth gating on `/`, static assets served, and a contract test asserting every `getElementById` in `app.js` has a matching `id` in `index.html`) lives in `test_auth.py` instead, since it needs the real app but no browser.
